This External Module is designed to assist you in renaming usernames within REDCap. While renaming can be necessary, it may also have serious implications for auditing and data integrity. PROCEED WITH CAUTION.

Before You Begin

  1. Review and Validate Everything Carefully
    • You are responsible for verifying all SQL, tables, and columns used by this module.
    • Double and triple check the generated SQL statements before running them.
    • Preview the SQL before any changes are made. Review all code line by line.
  2. Ensure Username Validity
    • New usernames must comply with REDCap’s requirements.
    • Allowed characters: letters, numbers, underscores (_), hyphens (-), and periods (.)
  3. Backup First
    • Create a full backup of your REDCap database.
    • Make sure you know how to restore from this backup if anything goes wrong.

If used interactively, the module appends a comment in the user_comments column of the redcap_user_information table to record the change with the date and time.

Important Notes on Database Integrity

For example: orphaned data in a child table could stop the script.

When updating multiple usernames, a failure might leave some usernames unchanged.

REDCap installations can vary. Some tables might be missing or differently structured, especially if your version is newer than the module.

How SQL Safe Updates Work

When enabled (= 1), MySQL will prevent:

  • UPDATE or DELETE statements without a WHERE clause.
  • Statements that don’t use a key in the WHERE clause.

When used interactively, the redcap_user_information table, column user_comments is appended with the date and time of the change.

SQL Update Explained

The SQL statement below is one line of the SQL code that performs the username change on a single table.

This command updates the redcap_auth table so that any user with the username bruce is changed to caitlyn, and it does so in a way that carefully preserves the exact text format.

UPDATE redcap_auth
  SET `username` = CAST(CONVERT("caitlyn" USING LATIN1) AS CHAR CHARACTER SET UTF8MB4)
  WHERE `username` = 'bruce'";
UPDATE redcap_auth
  SET `username` = CONVERT(BINARY CONVERT("caitlyn") USING utf8mb4) 
  WHERE `username` = "bruce";

It is trying to bypass or neutralize any collation or character set mismatches by explicitly converting the string encoding.

What this does:

  1. CONVERT("caitlyn" USING LATIN1)
    - This interprets the string 'caitlyn' as if it were stored in the latin1 character set.
    It’s not changing the bytes, but rather telling the database: “Treat these bytes as if they were latin1-encoded."
    Example use case: If a string was originally saved using latin1, but the database now uses utf8mb4, this prevents misinterpretation during conversion.
  2. CAST(... AS CHAR CHARACTER SET utf8mb4)
    This converts the result of the CONVERT(...) into a proper UTF-8 string.
    It ensures the data is interpreted and stored as valid utf8mb4 text.

Putting it all together:
You’re taking a string that may have been mis-encoded or stored under the wrong character set (latin1), and converting it safely into utf8mb4. This helps avoid corrupted text, question marks (�), or other encoding problems when moving between database versions or character sets.

  • Global MySQL/MariaDB character set or collation settings
  • Table or column-level charset/collation

Why?

  • If you’re updating values that came from a system with a different character encoding (e.g., latin1 source to utf8mb4 destination).
  • To avoid collation conflicts in WHERE clauses or assignments, especially when STRICT_TRANS_TABLES or NO_ENGINE_SUBSTITUTION is enabled.
